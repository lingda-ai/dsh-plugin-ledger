# 账本（dsh-plugin-ledger）商业计划书

> 主体：灵搭 / LingDaAi（独立产品线，不与任何其他公司主体混用）
> 版本：v0.1 · 2026-11
> 配套：技术文档 `docs/technical.md`、协议 `docs/wire-format.md`

---

## 1. 一句话定位

**AI 编程的成本仪表盘，从"这个会话为什么贵"做到"这个团队的钱花得值不值"。**

不是计费系统，不是调试追踪器——是一个**让人敢开 AI 而不怕账单**的工具。

---

## 2. 机会

### 2.1 痛点是真的，而且正在变大

AI coding 的成本结构有三个特征，让传统工具都不适用：

1. **价格不透明**：同一份 token，命中与未命中差 50 倍；订阅制和按量制混在同一个团队里，没人说得清总账。
2. **归因困难**：一次对话花了 ¥0.05，是模型贵、工具吐了 18k 字符、还是压缩没生效？只有一个数字，没有解释。
3. **决策缺依据**：工程师不知道还能问几次；管理者不知道该不该给某个项目加预算。

### 2.2 现有工具都只解了一半

| 类型 | 代表 | 解决什么 | 缺什么 |
|---|---|---|---|
| 追踪调试 | LangSmith / Langfuse | 链路、prompt、evaluation | 不做钱，不做治理 |
| 单工具用量面板 | 各 IDE 自带的 usage | 自己的 token 数 | 只看自己，跨工具为零，无归因 |
| 云账单 | 厂商控制台 | 最终金额 | 滞后、无明细、无归因、不跨厂商 |
| 财务系统 | ERP / 报销 | 对账、发票 | 看不到"花在哪一步" |

**空白区很清楚**：跨工具、能归因、敢说"不知道"、能和账单对账的中间层。

### 2.3 三类客户，价值主张不同

| 客户 | 规模 | 他们在意什么 | 愿意为谁付钱 |
|---|---|---|---|
| 个人开发者 | 1 人 | 别把钱烧在看不见的地方 | 免费（用开源版） |
| 中小团队 | 5–50 人 | 谁在烧、该不该管 | 团队版订阅 |
| 企业 / 国企 | 50+ 人 | 合规、审计、账单对得上 | 私有化 + License |

## 3. 产品结构：三档，一条清晰的分界线

```
┌─────────────────────────────────────────────┐
│ 企业版   私有化 + License + 等保材料         │  对账、审计、数据不出域
├─────────────────────────────────────────────┤
│ 团队版   多端汇聚 + 人/项目维度 + 预算治理    │  ← 商业分界线
├─────────────────────────────────────────────┤
│ 开源版   单会话账本（已上线）                 │  免费，全功能不阉割
└─────────────────────────────────────────────┘
```

**分界线是「会话账本 → 团队账本」，不是更多图表。**
开源版回答"这次会话贵不贵"，团队版回答"这个部门这周花了多少、该不该管"。
两者之间不是功能多少的差别，是**有没有治理能力**的差别。

### 3.1 开源版（已可用）

- 四档计价、缓存节省额、工具体积归因、压缩前后对照、预算与"还能问几次"
- 单会话 + 跨会话对比
- 三条铁律：采集只订阅、决策只改配置、未知即未知
- Apache-2.0，允许商用集成（含私有化），不收授权费

### 3.2 团队版（未开工，需先验证）

| 能力 | 为什么值钱 |
|---|---|
| 多端汇聚 | 一台机器一个孤岛，团队要一张总表 |
| 按人/项目维度 | 归因到人才能治理，归到插件只能自省 |
| 三级预算（组织/项目/个人） | 超限告警给管理员，而不是提示模型自己压缩 |
| 周报推送（飞书/企微/钉钉） | 让人不用打开面板就能被提醒 |
| 异常检测 | "某人今天花了日均 10 倍"比阈值告警更有用 |
| 数据保留与脱敏策略 | 合规底线，不是可选项 |

### 3.3 企业版

- 私有化部署（Docker Compose 起步，K8s 可选）+ License 授权初始化
- **账单对账**：采集到的金额 vs 厂商账单，出差异报告
- 审计日志不可篡改、数据不出域、三级等保材料
- 与财务系统导出对接（CSV/Excel，不承诺发票）

## 4. 差异化：三条别人不容易抄的

### 4.1 敢说「不知道」

竞品普遍把缺失数据填成 0 或估算值，让报表看起来完整。账本的做法相反：

- 费率缺失 → `— no-rate`，合计旁边写「其中 N 条费率未知，合计偏低」
- 省下的 token 属命中还是未命中无法推断 → **只报 token，不折钱**

短期看"不够漂亮"，长期看这是**唯一能被财务信任的报表特征**。

### 4.2 缓存节省额是严格算出来的

```
saved = cacheReadTokens × (input 单价 − cacheRead 单价)
```

两个单价同表、差额确定，不需要任何假设。这是市面上少见的"可审计的省了多少钱"。
客户看到「缓存命中已省 ¥0.0153 · 占应花 25.1%」，才会相信这个工具在帮他省钱，而不只是在报数。

### 4.3 协议为多工具而生，不是一个工具的皮肤

计量用 `measures[]`（单位+数值），token 只是其中一种单位；席位订阅用 `seat.month`。
幂等键 `sha1(session|turn|step|operation)` 解决双端重复入账。
这两件在只有一个来源时就锁定，意味着第二个工具接入的成本是"一张映射表"，不是一次重构。

## 5. 定价

### 5.1 原则

**不为功能加锁，为治理收费。** 开源版全功能免费，付费买的是"跨人、跨工具、可对账"。

锚定逻辑：团队版价格 ≈ 客户被管住的 AI 支出的 10–15%。一个 20 人团队每月 AI 花费 ¥3000–8000，
年付 ¥3600–7200 属可接受区间。

### 5.2 建议价目

| 档位 | 价格 | 门槛 | 说明 |
|---|---|---|---|
| 开源版 | ¥0 | — | Apache-2.0，可商用集成 |
| 团队版 | **¥180 / 人 / 年** | 10 人起（¥1800/年） | 含汇聚、人/项目维度、三级预算、周报 |
| 团队版·年付优惠 | ¥150 / 人 / 年 | 20 人以上 | 降低决策成本 |
| 企业版 | **¥3–8 万 / 年** | 按规模 | 私有化 + License + 等保材料 + 对账 |
| 一次性部署服务 | ¥1–3 万 | 可选 | 私有化实施、集成、培训 |
| 知识付费（DSH 插件开发） | ¥299–999 / 课 | — | 引流 + 品牌，与主产品互补 |

> 所有价格是建议，需 owner 拍板。企业版区间取决于是否含等保测评配合工作。

### 5.3 为什么不卖"按用量抽成"

按 token 抽成会把账本变成计费系统，接着就要背对账、发票、调价追溯、税务口径——那是财务产品的活。
**账本只回答"钱花在哪、谁花的、值不值"，可以导出给财务，但不替财务下结论。** 这条边界必须守。

## 6. 增长路径

### 阶段一：开源铺开（现在 → 3 个月）

- Gitee 主仓 + npm 生态发布（`dsh-plugin-ledger`）
- 目标：**50–200 个真实安装**，不是 star 数
- 内容：技术文档已在写（原理级）；再补 3 篇——"为什么缓存命中差 50 倍"、"压缩到底省不省钱"、"我们为什么不填 0"
- 渠道：DSH 社区、Gitee 推荐、掘金/知乎技术长文
- 验证门槛（决定是否继续投入）：**有 5 个以上外部用户持续使用两周**、至少 3 个真实反馈

### 阶段二：团队版最小闭环（验证通过后 → 6 个月）

只做一件事：`本地流水 → 批量上报 → 一页「本周按人/按项目」视图`。

- 需要三块底座：身份绑定（已有线索）、上报通道、共享计价包
- 硬指标：上报过程**不影响插件热路径**（旁路定时器，性能门禁不得退化）
- 定价试水：先做 3–5 家种子客户（¥180/人/年），换取真实账单数据

### 阶段三：企业版（有 2 家以上付费企业后）

- 私有化打包 + License 初始化
- **账单对账**是这一档的核心卖点：采集 ¥4300 / 账单 ¥4600 / 差 ¥300 怎么来的
- 等保材料配合

## 8. 财务假设（明确标注：全部为假设，不是预测）

假设前提：由 1 名主力开发 + 兼职支持推进；不投广告；靠技术内容与生态自然增长。

| 指标 | 保守 | 基准 | 乐观 |
|---|---|---|---|
| 12 个月安装数 | 200 | 800 | 2000 |
| 付费转化（安装→付费） | 1.5% | 3% | 5% |
| 付费席位 | 3 家 × 12 人 | 8 家 × 18 人 | 20 家 × 25 人 |
| 团队版 ARR | ¥6,480 | ¥43,200 | ¥150,000 |
| 企业版客户 | 0 | 1 家 ¥5 万 | 3 家 ¥15 万 |
| 知识付费收入 | ¥3,000 | ¥15,000 | ¥40,000 |
| **合计年收入** | **≈ ¥9,500** | **≈ ¥11 万** | **≈ ¥34 万** |

**这个模型的意义不是收入预测，而是验证路径**：第一年收入不构成商业模式证明，
真正的信号是"付费转化率"和"企业客户数"。如果 12 个月后付费 < 3 家，问题在价值主张而不在功能。

## 9. 风险与边界

| 风险 | 应对 |
|---|---|
| **做成计费系统** | 死守边界：不承诺"这是你该付的钱"，只做归因与对账 |
| **采集合规** | 开源版默认全关（面板/流水/落盘三个开关）；只记体积不记内容；绝对路径不入账 |
| **第三方工具本地数据** | 需用户显式授权 + 本地脱敏；企业版提供"仅账单模式"（不装本地采集） |
| **订阅摊销口径争议** | 提供两套视图（边际 / 总拥有）并明示口径，绝不裸加总 |
| **宿主契约变化** | 三项契约已核实并写入 `docs/spikes.md`；SKIP≠通过的门禁防止假绿 |
| **单点依赖 DSH** | 协议已为多来源设计（measures + source 字段），第二个 adapter 是映射表工作量 |
| **开源被白嫖** | 接受。开源版就是引流层，付费层是治理能力，不靠加锁 |

## 10. 需要 owner 拍板的四件事

1. **仓库可见性**：现在是私有，开源引流需要转公开（Gitee 后台一键）。
2. **npm registry**：`private: true` 何时去掉、发到 npmjs 还是 Gitee Package。
3. **定价数字**：¥180/人/年 是否接受，企业版区间上限。
4. **团队版是否现在动工**：本人建议先看 M2 的验证门槛（5 个持续用户），再决定是否投 M3。

## 附：不做的事（同样重要）

- 不做 prompt 内容存储与分析（隐私红线）
- 不做模型效果评估（那是 LangSmith 的领域）
- 不做发票与税务口径
- 不做"AI 省了多少钱"的营销数字（只报能严格算的缓存节省）
