# 产品迭代路线（0.2 → 1.0）

> 定位不变：**AI 编程的成本仪表盘，从"这个会话为什么贵"做到"这个团队的钱花得值不值"。**
> 本文只写"按什么顺序做、做到什么算完"，商业模型见 `business-plan.md`，技术取舍见 `technical.md`。

## 0. 现状（0.1.12，2026-11）

已经能回答"这次会话花了多少"，但只回答了**一个会话**、**一个瞬间**、**一个屏幕**。

| 能力 | 状态 | 限制 |
|---|---|---|
| 单会话四档计价 + 缓存节省 | ✅ | 依赖价表命中模型名；未知一律显式 `—` |
| 右栏面板（标题/约几分/距现在/复制摘要） | ✅ | 只读一个会话；数据来自 3 秒节流的快照 |
| `ledger_query`（4 个 op） | ✅ | Agent 主动查，不是用户主动看 |
| 费率覆盖 `pricing.json` | ✅ | boot 时读一次，改完要重启 |
| 预算守卫（阈值 + 降级） | ⚠️ 代码在，**产品上没有入口** | 需手写 YAML；通道 A 还需宿主提供 messageFactory |
| 行为流水 trace | ⚠️ 默认关，开了会累积 | 字节上限按字符算（CJK 会超），会话结束不清理 |
| 历史 / 跨会话总账 | ❌ | 会话结束**快照即删**，昨天花了多少无从查起 |
| 导出 / 周报 | ❌ | 只有一个"复制摘要"按钮 |
| 团队聚合 / 上报 | ❌ | `wire.js` 协议是死代码，一条不发 |

**一句话**：单点体验刚跑通，产品能力还是一条竖线（一个会话），不是一个面（时间 × 项目 × 人）。

## 1. 判断依据（为什么是这个顺序）

三条来自真实使用与三轮审计的证据：

1. **"装完看不到数"是最大流失点**。这件事我们花了 5 个版本才修好（ESM 产物 → inject → remote 访问 → 轮询竞态）。**同类问题不能靠人肉排查**，必须有自检和门禁。
2. **用户看完数字不会改行为**。面板给出"缓存已省 97%"，但没人因此改过一次用法。价值闭环缺"下一步该做什么"。
3. **没有历史就没有商业**。团队版要卖的是"这周花了多少、该不该管"，而当前连"昨天"都查不到。

## 2. 路线图总览

| 阶段 | 版本 | 主题 | 工程量 | 出口标准 |
|---|---|---|---|---|
| **P0** | 0.2.x | 把地基打牢：可信、可查、可诊断 | 8–10 人日 | 崩溃 0；面板首次有数率 ≥95%；CI 门禁不再假红 |
| **P1** | 0.3.x | 从"看见"到"改变"：预算 + 省钱建议 | 10–12 人日 | 有用户因为面板改了行为（预算配置率/建议采纳率 >0） |
| **P2** | 0.4.x | 个人版完整：历史、总账、导出 | 12–15 人日 | 能回答"本周/本月花了多少"，可导出周报 |
| **P3** | 0.5.x–1.0 | 团队版底座：上报 + 聚合 + License | 8–12 周 | 3–5 家种子客户能用一页总表 |

**闸门**：P3 不先开工。触发条件是 `business-plan.md` 的 M2 验证——**≥5 个外部用户持续使用两周**。达不到就回补 P1/P2。

## P0 · 0.2.x 打地基（先做这个）

> 目标：让"这个面板是不是坏了"从一个人肉排查的问题，变成一个能自己说话的产品。

### P0-1 自检报告（doctor）｜S｜下一项

**问题**：过去 5 轮故障里，用户能看到的只有"没数据"或一句英文错误。

**做法**：面板底部加一个可折叠的「诊断」区，一行一项，绿/黄/红：

| 检查项 | 判据 |
|---|---|
| Host 半已加载 | `ctx.ledger` 服务存在（面板能拿到快照就说明在） |
| 快照通道 | 最近一次 `fetchView` 的耗时与结果（成功/错误码） |
| 快照新鲜度 | `generatedAt` 距今 > 60s 标黄，> 10min 标红 |
| 费率来源 | 内置 / 自定义文件 / 自定义文件被拒（附原因码） |
| 价表命中 | 最近 N 条里有几条 `no-rate`；模型名与价表差在哪 |
| 预算 | 未配置 / 已用 X% |
| 落盘目录 | 实际路径 + 文件是否存在 |

**验收**：新增 `test/panel-doctor.test.mjs`（三种状态各断言一次）；README 加一节「面板没数怎么自查」，把支持成本从"问我"变成"看这里"。

**为什么不先做别的**：它直接决定"用户遇到问题会不会卸载"，而且实现只是把已有信息组织起来，风险最低。

### P0-2 历史落到磁盘（持久化）｜M｜✅ 0.1.13 已落地

**问题**：`session/disposed` 时快照被删除，账本只在内存。昨天、上周的钱查不到。

**做法**：新增 `<dshHome>/ledger/archive/YYYY-MM-DD.jsonl`（或一个 SQLite，二选一）：

- 每条 = `{ sessionId, sessionTitle, at, kind, route, usage, cost, attribution }`（**不含任何对话文本**，与 trace 同口径）
- 写盘走现有 `trace-file` 的"入队 + 合并写"，热路径零 IO
- 会话结束把当次快照并入归档，再删除工作区快照
- 保留策略：默认 90 天，超出按日期裁剪

**验收**：`test/archive.test.mjs`——跨会话写入、按天分片、90 天裁剪、损坏行跳过不炸、热路径基准不退化（`bench --gate` 相对基线）。

**取舍**：不做数据库迁移框架，先 JSONL；真到百万行再换 SQLite（那时正好是团队版）。

### P0-3 修掉审计遗留的中危项｜S｜一次性清账

| 项 | 现状 | 修法 |
|---|---|---|
| trace 字节上限用字符数 | CJK 下 64KB 上限写出 120KB | 改用 `Buffer.byteLength`，并补 CJK 用例 |
| trace 文件不回收 | 单文件 4MB 封顶，但会话结束不删 | 归档/删除策略与 P0-2 合并 |
| `pricingMetaOf` 丢 `detail` | `read-failed` 的 `EACCES` 到不了面板（两处死代码） | 透传 `detail`，面板显示原因 |
| `store.recordEntry` 收未归一化 usage | `cacheRead` 可能是 NaN，污染整会话汇总 | 入口归一化或断言 |
| `panel.dir` 与客户端读路径 | 已告警，但自定义 dir 面板仍读不到 | 客户端从 payload 里的 `panelDir` 读，或干脆禁用非默认值 |
| LRU / 8 步窗口 / 容量边界 | 无测试 | 按审计清单补 `store-bounds.test.mjs` |

**验收**：以上每条都有对应测试；`bash scripts/ci.sh` 全绿。

### P0-4 门禁不再假红｜S

**问题**：`bench --gate` 用绝对阈值，机器一忙就红（实测 load 88 时 LRU 抖动 15.8µs vs 阈值 15µs），久了大家会忽略它。

**做法**：改成**相对基线**——记录上次通过的基线（`.bench-baseline.json`），本次超过基线 1.3 倍才失败；基线只在 main 上更新。

**验收**：同一台机器连跑 5 次不出现假红；人为注入 2 倍退化时必红。

### P0-5 300px 与暗色｜S｜打磨

- 300px 是硬约束，目前只有截图没有自动化：加样式契约断言（关键行 `nowrap + ellipsis`、区块顺序、不出现横向滚动）。
- 暗色模式：宿主有主题服务时跟随（`prefers-color-scheme` 兜底），颜色集中成一组 token。

## P1 · 0.3.x 从"看见"到"改变"

> 目标：用户第一次因为面板**改了行为**。这是留存的分水岭。

### P1-1 预算入口（不写用户配置）｜S

面板内给三档预设（¥0.5 / ¥2 / ¥5），点一下 → **生成可复制的配置片段** + 一句"粘到 profile 的 cordis.patch.yml"。
不直接改用户配置文件：插件没有写 profile 的合法通道，硬写属于越权。

**验收**：复制内容能被 `resolveConfig` 正确解析（用真实 YAML 解析断言）；`budget.limit=0` 不当作启用。

### P1-2 超预算提醒（两条通道都做）｜M

- **面板**：合计条转琥珀 + 一句"已超预算 X%，还可约 Y 次"。
- **Agent 侧**：走通道 A（`agent.inject` 一条预算事实），前提是宿主提供 `messageFactory`；拿不到就只做面板 + `ledger_query` 主动查询提示。

**验收**：`test/budget-alert.test.mjs`；回滞语义（跨阈值只提醒一次，低于 0.9×阈值才重新武装）保持不变。

### P1-3 省钱建议（这是产品真正值钱的地方）｜M

三条可以从现有数据算出来的建议，每条都带**可执行动作**与**预计节省**：

| 建议 | 触发条件 | 话术 |
|---|---|---|
| 缓存前缀失效 | 某步 `cacheRead` 骤降到 <10% 且上下文 > 5 万 tok | "第 7 步前缀变了，这步多花了 ¥X；把系统提示/开场放在最前能恢复命中" |
| 工具结果过大 | 单步 `contextChars > 20k` | "这步的工具结果 24k 字符，占这一步成本的 62%；让它只返回摘要" |
| 模型错配 | 某模型单价 > 全局均价 3 倍且单步 < 2k 输出 | "这一步用了 pro 但只产出 800 tok，换 flash 可省 ¥X" |

**验收**：每条建议有"为什么这么判断"的依据行（不能是黑箱）；建议必须在**能算出来时**才出现，算不出来就闭嘴（沿用"未知即未知"铁律）。

### P1-4 首次引导（1 分钟上手）｜S

装完第一次打开面板 → 三屏卡片（这是什么 / 会记录什么 / 关了面板也在记账），可跳过，只出现一次（记在 storage）。

## P2 · 0.4.x 个人版完整

### P2-1 总账视图｜M
跨会话、按天、按项目（`identity.project` 已有）的聚合页；时间范围切换（今天/7 天/30 天）。

### P2-2 导出｜S
CSV（明细）+ Markdown 周报（复用"复制摘要"的排版）。周报模板固定，不引入模板引擎。

### P2-3 保留与清理｜S
默认 90 天；面板里能看"占用多少、下次清理时间"，提供"立即清空"。

### P2-4 性能与内存门禁｜S
300k 事件后 <32MB 已在 bench 里；再补"长会话 100 万事件"的门槛，防止历史归档拖慢热路径。

## P3 · 0.5.x → 1.0 团队版底座（有闸门）

只做一件事：**本地流水 → 批量上报 → 一页「本周按人/按项目」**。

| 子项 | 说明 | 工程量 |
|---|---|---|
| 上报通道 | `wire.js` 协议现成（`measures[]` + 幂等键），加旁路队列、批量、断网续传、失败退避 | 4–6 人日 |
| 聚合服务 | 最小实现：接收 + 按人/项目/天分组 + 一页 HTML | 4–6 人日 |
| 身份与隐私开关 | deviceId/actor/project 已采集；上报需显式开启 + 文档说明字段清单 | 1 人日 |
| License（企业版） | 私有化安装包 + 激活码校验 + 等保材料清单 | 见 business-plan M7 |

**硬约束**：上报不得进入热路径（旁路定时器），`bench --gate` 不得退化。

## 3. 每版的 Definition of Done

一个版本能发，必须同时满足：

1. **三种状态都有渲染断言**：正常 / 空 / 错误（少一种就是"用户会看到空白"）。
2. **至少一条跨模块端到端**测试（Host 写 → 客户端读；或产物渲染）。单模块测试全绿不算过。
3. **产物测试通过**：`lib/client.js` 由源码重建后与提交一致（CI 已强制）。
4. **门禁全绿**：`bash scripts/ci.sh`（bench 用相对基线）。
5. **文档同步**：README 的开关表、technical 的取舍、本文的进度勾选。
6. **崩溃零容忍**：任何客户端改动都必须过 `client-artifact-render`。

## 4. 衡量"用户喜欢"的指标（先埋点，再谈值）

| 指标 | 怎么来 | 目标 |
|---|---|---|
| 面板首次打开有数率 | 快照存在且 `entries>0` 的比例 | ≥95% |
| 崩溃/错误率 | 客户端 `[ledger]` warn 计数（本地） | 0 |
| 复制摘要使用率 | 按钮点击（本地计数） | ≥15% 会话 |
| 预算配置率 | 配置了 `budget.limit` 的比例 | ≥20%（P1 后） |
| 建议采纳率 | 建议出现后 7 天内相关指标改善 | 先观察，不设目标 |
| 7 日留存 | 安装后第 7 天仍有面板访问 | ≥40% |

> 全部**本地统计、不上报**（团队版才谈上报，且需显式开启）。

## 5. 风险与不做的事

| 风险 | 应对 |
|---|---|
| 厂商自带成本面板 | 我们的差异是**跨工具 + 敢说不知道 + 可对账**，不跟厂商比"余额" |
| 做成计费系统 | 死守边界：不给"你应该付的钱"，只做归因与对账 |
| 数据采集越界 | 只记体积不记内容；绝对路径不入账；历史默认 90 天 |
| 宿主契约再变 | 每类契约都留一条"真机语义"回归测试（已三次教训） |

**不做**：prompt 内容分析、模型效果评估、余额查询、按 token 自动省钱（替用户做决定）。

## 6. 现在就要拍板的三件事

1. **P0-1 自检** vs **P0-2 持久化**：我建议先 P0-1（1–2 天，立刻降低支持成本），再做 P0-2（3–4 天，是 P2/P3 的地基）。
2. **归档格式**：JSONL（简单、可 grep、零依赖）还是 SQLite（查询快、要引依赖）。建议先 JSONL。
3. **P3 闸门**：是否坚持"5 个持续用户"再动上报通道——这条决定要不要现在花 10 人日写服务端。
